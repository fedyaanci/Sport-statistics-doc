# Как рассказать третью лабораторную

## Рассказ на одну-две минуты

«В третьей лабораторной я подготовил исходные сведения для проектирования приложения спортивной статистики: введение, архитектурные факторы и единый словарь. Структура взята из предложенного репозитория, содержание связано с моими Event Storming и User Story Map.

Во введении я определил цель, пользователей и границы продукта. Система сначала принимает достоверные спортивные действия и утверждает результат, а затем предоставляет статистику, видео, материалы и прогнозы.

Функциональные требования описывают, что делает сервис. Нефункциональные задают проверяемое качество. Например, повтор команды не должен давать второй гол, конкурентная правка не должна затирать чужую, а табло должно показывать новую версию с заданной задержкой.

Я использовал конкретные условия и способ проверки вместо слов “быстро” и “надёжно”. Для пилота предложил 20 читателей и 2 операторов. Целевые значения — одна секунда для p95 спортивных команд, две для чтения и три для p95 видимости изменения на табло. Эти числа — проектные допущения, их ещё надо проверить реализацией.

В словаре разделил похожие понятия: аккаунт и игрок, сезонная заявка и состав матча, завершение игры и подтверждение результата, архив и резервная копия. Эти названия будут использоваться и в коде.

Для реализации предлагаю Python, Django и PostgreSQL. Django объединяет обычные веб-возможности и сокращает число дополнительных библиотек, PostgreSQL подходит связанным данным и совместной записи. Интерфейс можно сделать шаблонами с небольшим JavaScript. Распределённая инфраструктура для небольшого пилота пока не обоснована».

## Короткие ответы

| Вопрос | Ответ |
|---|---|
| Что такое архитектурный фактор? | Требование или ограничение, которое заметно влияет на устройство системы и компромиссы |
| Пример функционального требования? | Оператор может зарегистрировать игровое действие с участниками и временем |
| Пример качества? | В условиях P0 p95 времени спортивной команды не более 1 секунды |
| Почему условия важны? | Задержка без объёма данных, нагрузки и начала/конца измерения неоднозначна |
| Что означает p95? | Не меньше 95% измерений укладываются в указанный порог; это не обещание максимума для каждого запроса |
| Почему не «всё real-time»? | Для табло определены версия, измеримая задержка и поведение при потере связи |
| Откуда числа? | Это явно помеченный небольшой профиль пилота, предложенный на основе сценариев; не реальные замеры и не скопированные тысячи пользователей |
| Зачем словарь? | Чтобы один термин означал одно и то же в требованиях, ES, интерфейсе и коде |
| Почему Django, а не FastAPI? | В проекте много форм, аккаунтов, связей и административных операций; Django даёт их основу вместе |
| Почему не SQLite? | Для первого упражнения можно, но пилот уже проверяет параллельную запись и версии; выбрана одна БД для разработки и приёмки |
| Где подтверждение производительности? | Пока есть требование и методика проверки. Результаты появятся после реализации и измерений |
| Что входит в ЛР3? | Только папка исходных сведений; пояснение стека приложено отдельно. Технический проект и процессы разработки относятся к следующим работам |

## Один пример фактора полностью

**DAT01 — защита от повторного учёта.** Оператор отправил действие, но не получил ответ из-за обрыва связи. Клиент повторяет тот же ключ запроса. Система возвращает прежний результат. Проверка: сто повторов, включая параллельные, дают ровно одно принятое действие и один вклад в счёт. Поэтому нужны сохраняемый ключ и согласованная операция записи.

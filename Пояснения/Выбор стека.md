# Небольшой стек и обоснование выбора

Это пояснение к третьей лабораторной и предпочтениям автора. Основной результат ЛР3 — три документа в «1. Исходные сведения». Здесь предлагается техническая основа для последующего проектирования; код приложения и формальные ADR ещё не создаются.

## 1. Предлагаемый вариант

**Python + Django + PostgreSQL**, серверные HTML-шаблоны, обычные CSS и небольшой JavaScript для обновления табло.

| Средство | Задача в проекте | Почему подходит |
|---|---|---|
| Python 3.13.x | Прикладные правила и расчёты | Автор предпочитает Python; одного языка достаточно для веб-логики, обработки данных и служебных команд |
| Django 5.2.x LTS | Веб-приложение, формы, ORM, миграции, пользователи, сеансы | Значительная часть обязательной инфраструктуры уже находится в одном фреймворке |
| PostgreSQL 18.x | Связанные данные и транзакции | Матчи, игроки, действия, версии и назначения естественно связаны; SQL знаком автору |
| Psycopg 3 | Соединение Django с PostgreSQL | Один штатно поддерживаемый драйвер; отдельная ORM не нужна |
| Django Templates + HTML/CSS | Формы, таблицы, страницы статистики | Пользовательские страницы создаются в том же проекте без отдельного клиентского приложения |
| Небольшой JavaScript с `fetch` | Обновление открытого табло | Для принятой задержки сначала достаточно периодического HTTP-запроса; отдельный JS-фреймворк не нужен |
| Файловое хранение | Сохранённые отчёты, изображения и видео | В метаданных БД хранятся ссылки и состояния; сами большие файлы — в выделенном каталоге с контролируемым доступом и копированием |

Последние исправления выбранных веток фиксируются при начале разработки. На дату проверки Django 5.2 является поддерживаемой LTS-веткой с расширенной поддержкой до апреля 2028 года; Python 3.13 входит в её поддерживаемые версии. Это подходит для следующего учебного семестра. Источники: [сроки Django](https://www.djangoproject.com/download/), [совместимость Python](https://docs.djangoproject.com/en/5.2/faq/install/).

PostgreSQL 18 — стабильная поддерживаемая ветка, срок поддержки указан до 14 ноября 2030 года. Django 5.2 поддерживает PostgreSQL 14+ и Psycopg 3.1.8+, поэтому выбранная комбинация допустима; используются актуальные стабильные исправления, а не development-сборки. Источники: [политика PostgreSQL](https://www.postgresql.org/support/versioning/), [БД в Django](https://docs.djangoproject.com/en/5.2/ref/databases/), [Psycopg](https://www.psycopg.org/psycopg3/docs/basic/install.html).

## 2. Почему Django

В твоём приложении много обычной веб-работы: аккаунты, сеансы, формы, связанные справочники, проверки, таблицы, права, версии и сохранение изменений. Django объединяет эти возможности, ORM и миграции в одном согласованном наборе. Серверные шаблоны позволяют писать страницы без отдельной сборки frontend. Официальный обзор: [Django at a glance](https://docs.djangoproject.com/en/5.2/intro/overview/), [Templates](https://docs.djangoproject.com/en/5.2/topics/templates/).

| Кандидат | Что даёт | Что потребуется решить для этого проекта | Решение |
|---|---|---|---|
| Django | Интегрированные модели, миграции, формы, шаблоны, auth и административные инструменты | Написать спортивные правила, области доступа и пользовательские экраны | Выбран: меньше отдельных интеграций для заданного объёма |
| FastAPI | Удобные HTTP API, проверка схем, OpenAPI | Подобрать хранение/миграции, формы или отдельный клиент, реализацию аккаунтов и административных сценариев | Хорош при приоритете API; в этом учебном браузерном продукте экономия менее очевидна |
| Flask | Небольшое гибкое веб-ядро | Собрать и согласовать средства хранения, миграций, аккаунтов и форм под проект | Возможен, но переносит больше решений на автора |

Сравнение — инженерная оценка общей работы над этим продуктом, а не утверждение, что другие фреймворки не умеют выполнять задачи. Проверены [возможности FastAPI](https://fastapi.tiangolo.com/features/) и [устройство Flask](https://flask.palletsprojects.com/en/stable/design/). Маленькое ядро фреймворка не обязательно означает меньше компонентов готового приложения.

### Что Django не сделает за нас

Встроенная система auth даёт пользователей, группы, разрешения и сеансы. Но проверку «этот оператор может менять именно этот матч», подтверждение почты, ограничения частоты и предметные заявки нужно реализовать явно. Готовые группы не заменяют область доступа. Это соответствует границам штатной [системы аутентификации Django](https://docs.djangoproject.com/en/5.2/topics/auth/).

Данные о спортивных правилах, причинах исправления, попытках формирования и версиях источника также остаются частью нашего приложения. Атомарные операции можно выполнять штатными [транзакциями Django](https://docs.djangoproject.com/en/5.2/topics/db/transactions/); сам фреймворк не выбирает верную границу бизнес-операции.

Встроенная админка полезна для внутренних справочников. Формы оператора матча и просмотр болельщика лучше сделать отдельными страницами. Админка не должна давать обход проверок и аудита прямой правкой счёта. Её назначение как внутреннего инструмента описано в [документации Django admin](https://docs.djangoproject.com/en/5.2/ref/contrib/admin/).

## 3. Почему PostgreSQL, хотя SQLite проще установить

SQLite подходит для первых упражнений и локального одноавторского прототипа. В лабораторной уже зафиксированы два оператора, одновременные изменения, проверки версий, связанные участники и многократные запросы табло. Поэтому разумно сразу проверять приложение на PostgreSQL, который затем останется в пилоте.

Это не утверждение, что SQLite не имеет транзакций или не умеет веб-приложения. Важна совместная запись и требуемое поведение конкретного проекта. Документация Django отдельно отмечает ограничения конкуренции SQLite и отсутствие эффекта `select_for_update()` на этом backend: [ограничения SQLite](https://docs.djangoproject.com/en/5.2/ref/databases/#sqlite-notes).

Знание SQL остаётся полезным: связи, ограничения уникальности, индексы, `JOIN`, `GROUP BY`, `COUNT`, `SUM` и анализ запросов нужны при работе через ORM. Для обычных операций используется одна ORM Django. Если сложная выборка требует SQL, запрос параметризуется; не вводятся параллельно SQLAlchemy и ещё один набор миграций.

Плата за выбор — нужно установить и обслуживать один сервер БД. Для учебного проекта это ограниченное усложнение, которое прямо связано с DAT01–DAT03 и совместной работой.

## 4. Как обойтись небольшим интерфейсом

Первый вариант: Django формирует HTML-страницу, сервер обрабатывает форму, возвращает ошибки или результат. Табло дополнительно запрашивает компактные данные через `fetch` примерно раз в секунду и показывает версию/время обновления.

Такой подход проверяется по PER03 и SCA01: он обязан уложиться в задержку и нагрузку пилота. Если измерения покажут необходимость постоянного соединения, это будет отдельным обоснованным изменением. Наличие слова «онлайн» само по себе не требует WebSocket.

Для MVP не нужны React/Vue, TypeScript, Node.js-сборка, Django REST Framework и отдельный сервер frontend. Обычный JavaScript остаётся частью браузерного интерфейса; писать всю клиентскую интерактивность на Python не предлагается.

## 5. Дополнения по релизам

| Когда | Задача | Небольшое дополнение / вариант |
|---|---|---|
| MVP | Таблицы и базовые показатели | SQL-агрегации и обычный Python; NumPy/Pandas не нужны для каждого подсчёта |
| MVP | Почта | Штатный SMTP-backend Django и внешний почтовый сервис; свой почтовый сервер не разрабатывается |
| Релиз 1 | Сохраняемый отчёт | Сформированный статический HTML-файл со снимком данных; при необходимости пользователь печатает его в PDF средствами браузера. Серверный PDF/DOCX-генератор не обязателен |
| Релиз 1 | Инфографика и график прогресса | Одна библиотека Matplotlib для PNG после согласования шаблонов; отдельный графический сервис не нужен |
| Релиз 1 | Видео | FFmpeg как утилита обработки, вызываемая приложением; исходник, готовый результат и попытка сохраняются раздельно |
| Релиз 1 | Длительные операции | Управляемая служебная команда того же проекта с сохраняемыми заданиями/попытками в БД. Детали восстановления выбираются в техническом проекте; поток в памяти не считается надёжной очередью |
| Релиз 2 | Первый вариант прогноза | Согласованная воспроизводимая методика на Python и SQL; большая ML-платформа не требуется заранее |
| Релиз 2 | Внешний импорт | Один адаптер выбранного источника, сохраняемый пакет, проверка и сопоставление; отдельный интеграционный сервер не нужен |

Matplotlib и FFmpeg относятся к функциям, которые впервые появляются в релизе 1. Они не объявлены обязательными зависимостями базового MVP. Выбор форматов и лимитов видео остаётся отдельным решением перед реализацией F12. Источники возможностей: [Matplotlib](https://matplotlib.org/stable/users/index.html), [FFmpeg](https://ffmpeg.org/ffmpeg.html).

Периодическое выполнение служебной команды можно организовать планировщиком ОС. Это второй процесс того же приложения, если он понадобится, а не новый независимо разрабатываемый микросервис. Celery и Redis можно рассмотреть позже при измеренной потребности в большом числе фоновых работ; они не включены в исходный набор.

## 6. Границы решения и затраты

Упрощение не отменяет контроль доступа, транзакции, версии, резервные копии и явные ошибки. Эти свойства потребуют кода и проверки. Одна установка также означает, что при её отказе пилот будет недоступен до восстановления; принятое SLO и RTO описаны в требованиях.

Предполагается локальная разработка в привычной IDE с `venv` и `pip`. Для сетевого пилота отдельно выбирается поддерживаемый сервер приложения и способ HTTPS. Встроенный сервер разработки Django не предлагается для сетевой эксплуатации. Контейнеризация может использоваться для удобства автора, но Docker и оркестрация не являются требованием ЛР3.

Не добавляются заранее Kafka/RabbitMQ, Redis, Elasticsearch, Kubernetes, отдельная NoSQL-БД и внешняя ML-платформа: для выбранного P0 нет подтверждённого фактора, требующего именно этих компонентов. Установка любого из них должна отвечать на конкретное ограничение, которое не устраняется более простым способом.

## 7. Связь выбора с требованиями

| Фактор | Почему выбранная основа разумна | Что ещё надо сделать |
|---|---|---|
| DAT01–DAT03, DUR01 | SQL-БД и транзакции позволяют согласовать принятие факта и версии | Правильно спроектировать ключи, ограничения и конкурентные операции |
| SEC01–SEC03 | Django даёт основу аккаунтов, сеансов и веб-защиты | Реализовать область доступа, подтверждение почты, политику ссылок/частоты и настройки HTTPS |
| F03–F08 | ORM, формы и миграции подходят связанным сезонным данным | Реализовать спортивные ограничения и пользовательские формы |
| PER01–PER03 | Прямой путь от Python-обработчика к БД и простые HTTP-обновления соответствуют небольшому профилю | Измерить запросы, индексы, задержки и исправить узкие места |
| F14–F17 | Python подходит формированию материалов и воспроизводимому расчёту | Согласовать форматы, параметры и методику |
| LIM01–LIM02 | Основные инструменты совпадают с предпочтениями и навыками автора | Изучить Django и один сервер БД вместо набора отдельных платформ |

Это обоснование исходного выбора по требованиям. Оно не является утверждением, что выбор автоматически обеспечивает производительность, безопасность или готовность всех функций.

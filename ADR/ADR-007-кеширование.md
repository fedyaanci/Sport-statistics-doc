# ADR-007. Выбор механизма кеширования

**Дата:** 9 ноября 2026 г.  
**Статус:** Принято

## Контекст

Карточки популярных матчей и команд могут одновременно читать многие пользователи. Повторный расчёт одинаковых агрегатов увеличивает нагрузку на PostgreSQL, однако устаревший кеш онлайн-табло нарушает требование актуальности.

## Рассмотренные варианты

1. **Не использовать кеш.** Каждый запрос обслуживается основным хранилищем.
2. **Локальный кеш процесса.** Быстрый, но не согласован между экземплярами.
3. **Redis.** Общее внешнее in-memory-хранилище.
4. **Memcached.** Распределённый кеш простых значений.
5. **Только материализованные представления PostgreSQL.**

## Решение

Использовать **Redis** по стратегии **Cache-Aside** для горячих представлений статистики, сессий соединения и ограничителей запросов. Источником истины остаётся PostgreSQL.

Ключ кеша содержит тип представления, идентификатор объекта и версию формата. TTL задаётся по типу данных: для идущего матча он не превышает допустимую задержку live-обновления; для завершённого матча может быть больше.

## Обоснование

- общий кеш работает при горизонтальном масштабировании серверов;
- TTL ограничивает время жизни устаревших данных;
- атомарные операции подходят для счётчиков и rate limiting;
- отказ кеша можно пережить, обслуживая запрос из PostgreSQL;
- Redis может использоваться как backplane SignalR, не становясь основным хранилищем.

## Ограничения и недостатки

- инвалидировать кеш сложнее, чем записать данные в одну базу;
- Redis добавляет сетевой вызов и отдельный компонент сопровождения;
- потеря кеша вызывает временный рост нагрузки на PostgreSQL;
- запрещено хранить в кеше единственную копию события, официального результата или задания;
- слишком длинный TTL ухудшает актуальность, слишком короткий снижает пользу кеша.

## Последствия

- код должен корректно работать при промахе и недоступности Redis;
- подтверждённое изменение матча публикует событие инвалидирования;
- для массового одновременного промаха применяются распределённая блокировка или случайное отклонение TTL;
- собираются метрики hit rate, времени ответа и ошибок Redis;
- чувствительные данные кешируются только при наличии обоснования и ограниченного срока жизни.

## Условия пересмотра

Решение пересматривается, если нагрузочные тесты показывают отсутствие пользы от общего кеша либо требования безопасности запрещают хранить выбранные данные в памяти внешнего процесса.
